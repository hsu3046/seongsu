# Seongsu Passport — UI 데모 조사 및 구현 제안

작성일: 2026-09-05  
상태: 2안 승인 / 첫 데모 구현·로컬 검증 완료  
입력 문서: [PRD v0.1](../doc/seongsu-app-prd.md)

TL;DR: 브라우저에서 직접 걸어 다니는 작은 도트 골목, 명소 상세, 시간대 전환, 여권 수집까지 구현하는 2안을 추천한다. 장소 5곳과 코스 1개로 제품의 핵심 경험을 확인한다. 실제 성수 지도 생성, 실사 촬영, 상용 앱 성능은 후속 검증 대상이다.

## 1. 확인한 현재 상태

아래 목록은 최초 조사 시점의 상태다. 이후 구현은 ARCHITECTURE.md와 VALIDATION.md에 기록한다.

- 프로젝트에는 PRD 한 개만 있다. 앱 코드, package.json, Godot 프로젝트, 사진, 타일셋, 3D 모델은 없다.
- 현재 디렉터리는 Git 저장소가 아니다.
- 이번 작업은 문서 검토와 공식 기술 문서 조사다. 엔진 실행, 실제 기기 성능 측정, 외부 데이터 API 재조회는 수행하지 않았다.
- PRD의 데이터 수량과 시장 사례는 PRD의 주장으로 취급하며, 이번 조사에서 독립 검증한 수치로 사용하지 않는다.

## 2. 구현 선택지

| 선택지 | 결과물 | 장점 | 비용·한계 | 대략적 작업량 |
|---|---|---|---|---|
| 1. UI 클릭 데모 | React로 시작·코스·장소·여권 화면, 지도 지점 클릭 | 화면 구성과 문구를 빠르게 검토 | 아바타 이동과 골목 탐험의 재미를 검증하기 어려움 | 1~2일 |
| **2. 웹 플레이 데모 — 추천** | React + TypeScript + Vite + Phaser로 이동·충돌·탐험·도장까지 연결 | 설치 없이 체험 가능하고 UI와 플레이를 함께 검토 | Godot 전환 시 화면·게임 로직을 다시 구현해야 함 | **3~5일** |
| 3. Godot 직접 제작 | Godot 4 + GDScript로 같은 코어 구현, 우선 데스크톱 실행 | PRD의 최종 엔진을 직접 검증하고 게임 코드를 이어갈 수 있음 | 엔진 환경·자산·내보내기 설정까지 초기 작업에 포함 | 1~2주 |

작업량은 개발자 1명, 단순한 자체 임시 아트, 코스 1개, 외부 콘텐츠 확보 대기 제외 조건의 계획 추정치다. 검증된 납기나 완성형 아트 제작 견적이 아니다. Godot 안의 iOS/Android 서명·스토어 배포는 별도 범위다.

2안은 이번 요청의 UI·체험 확인을 위한 제안이다. PRD의 최종 모바일 엔진을 웹 기술로 확정하는 결정은 아니다. 최종 앱을 Godot로 이어 만드는 것이 당장 우선이라면 3안이 더 적합하다.

## 3. 공식 자료에서 확인한 기술적 근거

- Phaser 공식 React/TypeScript 템플릿은 Vite와 React↔게임 통신 구조를 제공한다. UI와 게임 장면을 분리하는 출발점이 있다. 정확한 의존성 버전은 착수 때 호환성을 확인하고 고정한다. [공식 템플릿](https://github.com/phaserjs/template-react-ts)
- Phaser Arcade Physics는 사각형·원 충돌을 다루며 탑다운 게임에 맞는 가벼운 시스템이다. 이번의 보행·건물 충돌 요구와 잘 맞는다는 판단이다. [공식 물리 문서](https://docs.phaser.io/phaser/concepts/physics)
- Tiled는 JSON 내보내기를 지원한다. 장소·코스 데이터와 타일맵 소스를 화면 코드 밖에 보관하면 이후 엔진 변경 때 자산을 재활용하기 쉽다. Godot의 TMX 임포트 경로는 별도로 검증해야 한다. [Tiled JSON 문서](https://doc.mapeditor.org/en/stable/reference/json-map-format/)
- Godot도 웹 실행이 가능하다. 현재 문서는 단일 스레드 웹 내보내기를 기본으로 설명하며 macOS/iOS 호환 개선을 명시한다. 다만 웹은 WebAssembly·WebGL 2와 Compatibility 렌더러를 사용하고 모바일 성능·Safari 관련 제약이 있다. 따라서 Godot가 브라우저에서 불가능하다는 이유로 2안을 추천하는 것은 아니다. [Godot 웹 내보내기](https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_web.html)
- 브라우저에서 독립된 3D 뷰어를 넣는 기술 경로도 존재한다. 실제 공간 모델의 확보·경량화와 뷰어 UI는 별도 작업이다. [model-viewer](https://modelviewer.dev/)
- PRD의 Arnis는 실제 지형을 Minecraft 등의 월드로 생성하는 도구다. 처리 구조는 참고할 수 있지만, 성수용 2D 타일맵을 즉시 제공하는 완성 파이프라인으로 계산할 수는 없다. [Arnis 공식 저장소](https://github.com/louis-e/arnis)

## 4. 2안의 구체적 범위

목표는 사용자가 설명 없이 시작해서 3~5분 동안 골목을 돌아보고, 다섯 장소를 발견하고, 가상 방문 도장을 모아 코스를 완성하는 것이다. 체험 시간은 목표이며 플레이 테스트로 조정한다.

| 영역 | 첫 데모에서 실제 동작할 것 | 콘텐츠·검증의 한계 |
|---|---|---|
| 도트 월드 | 작은 골목 1개, 건물·골목 충돌, 카메라 추적, 4방향 이동 | 성수 분위기의 수작업 샘플 맵. 실제 지도 정확성·압축비 검증 대상은 아님 |
| 장소 | 상호작용 장소 5곳, 근접 시 진입 안내 | 가상의 데모 장소명·설명. 영업정보로 제공하지 않음 |
| 상세 화면 | 전체 화면 전환, 설명, 이미지 넘기기, 코스 저장 | 초기에는 사진 준비 상태 표시. 제공·직접 촬영 사진을 확보한 장소부터 연결 |
| 여권 | 방문별 1회 도장, 0/5~5/5 진행도, 완주 화면 | 가상 방문 수집이며 실제 매장 방문 인증·쿠폰은 아님 |
| 코스 | 카페와 붉은벽돌을 주제로 한 코스 1개, 다음 장소 안내 | 여러 코스 추천·실제 도보 시간 계산은 후속 |
| 시간대 | 아침·오후·밤, 조명 색·간판·NPC 수 변화 | 고정 연출 테이블. 실시간 혼잡도나 실제 영업 상태를 나타내지 않음 |
| 분위기 | 걷는 사람·강아지·배달 이동체 등 간단한 반복 애니메이션 | 단순한 자체 임시 스프라이트 사용 |
| 언어 | EN/JA UI, 장소 설명·안내 문구의 샘플 번역 | 자연스러움·관광 안내 정확성은 언어 검수 필요 |
| 저장 | 여권·선택 코스·시간대·언어를 로컬 저장 | 계정·기기 간 동기화 없음 |
| 모바일 | 세로 화면, 방향 패드, 상호작용 버튼 | 실제 iPhone·Android에서 조작감과 성능 측정 필요 |

소리·배경음악, 착장, QR, 파트너 대시보드, 기여 기능, Supabase 연결은 첫 데모 이후 확장으로 둔다. 3D는 핵심 동선이 작동한 뒤 별도 선택하며, 추가한다면 제공받은 GLB 또는 명확히 표시한 샘플 모델 1개로 회전·확대 기능을 확인한다. 샘플을 실제 매장 스캔처럼 제시하지 않는다.

## 5. UI와 아트 방향

방향은 **붉은벽돌 골목을 담은 작은 여행용 RPG와 종이 여권**이다. 주인공은 걸어 다니는 도트 장면이다.

- 월드: 정사각 타일의 탑다운 시점에 건물 정면이 조금 보이는 고전 RPG 표현. 붉은벽돌, 철제 셔터, 화분, 입간판, 전선, 작은 중정을 반복해 밀도를 만든다.
- 해상도: 데모는 32×32 타일을 가정한다. 아바타는 4방향×걷기 3프레임. 정수 배율과 선명한 픽셀 확대를 유지한다. 이것은 PRD Q3의 최종 아트 규격 확정과 구분한다.
- 색: 벽돌색·크림색·차콜·나뭇잎 녹색을 중심으로 제한된 팔레트. 밤에는 남색 바탕과 따뜻한 창문 불빛을 사용한다.
- 글자: 픽셀 폰트는 짧은 표식에 제한하고 설명문은 EN/JA 가독성을 확보한 글꼴로 표시한다. 폰트·자산의 라이선스는 사용 파일과 함께 기록한다.
- 모바일: 맵이 화면을 채우고 위에는 코스 진행도·시간대, 아래에는 이동과 상호작용 버튼. 여권은 별도 화면으로 연다.
- 데스크톱: 왼쪽 약 70%에 맵, 오른쪽에는 코스와 여권 요약. 게임 조작은 WASD/방향키와 상호작용 키로 제공한다.
- 상세 진입: 맵을 가리는 불투명 전환을 끝낸 후 사진·설명 전용 화면을 연다. 상세 화면 뒤로 픽셀 맵이 비치지 않게 한다.

초기 아트는 화면의 톤과 가독성을 확인하는 수준이다. 건물마다 차별화된 외관, 자연스러운 다방향 인물, 브랜드별 착장은 후속 제작 공수를 따로 잡는다. PRD Phase 0의 아트 외주 발주 유보 원칙은 유지한다.

## 6. 화면 흐름과 상태 규칙

1. **시작:** 여권 표지, EN/JA 선택, 코스 소개, 시작 버튼.
2. **탐험:** 아바타·골목·다음 목적지·진행도·시간대 제어. 첫 이동에 필요한 안내만 표시.
3. **장소 상세:** 장소 이야기·사진 영역·코스 저장·가상 방문 도장. 돌아가기로 원위치 복귀.
4. **여권:** 방문 도장, 남은 장소, 수집한 장소 설명으로 다시 진입.
5. **코스 완주:** 다섯 장소의 순서와 완주 여권. 다시 탐험하거나 진행도 초기화.

필수 상태 규칙:

- 상세·여권·설정 화면을 열면 이동 입력을 해제하고 게임을 일시정지한다. 복귀 때 캐릭터 위치·방향·카메라를 보존한다.
- 언어·시간대를 바꿔도 도장과 코스는 유지한다. 문 닫힘 연출 때문에 첫 코스가 완주 불가능해지지 않도록 구성한다.
- 도장 중복 발급을 막고 새로고침 뒤 수집 상태를 복원한다.
- 이미지가 없거나 로드에 실패해도 설명·돌아가기·도장 수집은 가능해야 한다.
- 저장이 불가능한 환경에서는 현재 세션으로 계속 플레이하고 저장 불가 상태를 알린다.
- 모바일 방향 패드에서 손을 떼거나 터치가 취소되거나 앱이 숨겨지면 이동을 멈춘다.
- 지도 이동 키가 상세 화면 스크롤을 가로채지 않게 하고, 화면 복귀 때 적절한 버튼으로 키보드 초점을 돌린다.
- 조작 버튼은 충분한 터치 영역을 확보하고, 상태를 색상만으로 구분하지 않는다. 짧은 전환 효과는 동작 줄이기 설정을 존중한다.

## 7. 구현 구조 제안

| 구성 | 책임 |
|---|---|
| React UI | 시작·상세·여권·완주 화면, 다국어, 접근성, 모바일 제어 버튼 |
| Phaser 장면 | 맵·충돌·아바타·NPC·카메라·시간대 시각 연출 |
| 공용 상태 | 선택 코스, 방문 장소 ID, 위치, 시간대, 언어 |
| 콘텐츠 파일 | 장소·코스 JSON, EN/JA 번역, 타일맵 데이터, 자산 출처 |
| 로컬 저장 | 버전이 있는 진행도 저장과 복원·초기화 |

프레임마다 변하는 아바타 좌표를 React 전체 화면 상태로 전달하지 않는다. UI에는 장소 진입·수집·화면 전환 같은 이벤트를 전달한다. 상세 화면 전환 시 입력과 게임 수명주기를 한 경로에서 관리한다.

Godot로 옮길 때 재사용 대상은 장소 ID, 코스 순서, 번역, 원본 아트, 충돌·상호작용 메타데이터와 플레이 검증 결과다. React 컴포넌트와 Phaser 장면 코드의 자동 이식은 전제하지 않는다.

초기 데모는 로컬 자산과 데이터만 사용한다. 서버 API, 로그인, 비밀키가 필요하지 않다. 새로 방문하는 오프라인 브라우저에서 실행되거나 오프라인 재로딩까지 보장하는 것은 별도 PWA 캐시 구현·검증 후의 범위다.

승인 후 React·Phaser 등의 실행 의존성과 Vite·TypeScript 등의 빌드 의존성은 프로젝트 안에 설치한다. 프로젝트를 초기화할 때 GNU GPL v3 LICENSE와 KnowAI 저작권 표기, 실행 안내 및 자산 출처를 함께 준비한다.

## 8. 단계별 진행과 완료 기준

| 단계 | 작업 | 완료 기준 |
|---|---|---|
| A. 화면 골격 | 시작·맵 HUD·상세·여권·완주, 팔레트와 반응형 | 휴대폰 세로 화면과 데스크톱에서 내용·버튼 잘림 없음 |
| B. 플레이 코어 | 작은 맵·아바타·충돌·카메라·장소 진입 | 키보드/터치로 건물을 통과하지 않고 다섯 장소에 도달 |
| C. 완결된 체험 | 도장·완주·저장·EN/JA·시간대·NPC | 한 코스를 끝까지 완주하고 새로고침 후 복원 |
| D. 검토·보정 | 실제 화면 확인, 입력·장면 전환 검증, 시각 보정 | 아래 시연 시나리오 통과 및 측정 결과 기록 |

첫 검토 시점은 A 완료 직후다. 이때 레이아웃과 도트 크기를 확인하고 B~D로 연결한다.

시연·검증 시나리오:

1. 처음 들어온 사람이 도움 없이 이동하고 첫 장소에 들어갈 수 있다.
2. 상세 화면에 들어갔다 나오면 위치가 유지되고 입력이 눌린 채로 남지 않는다.
3. 같은 장소를 반복 방문해도 도장이 늘지 않는다. 다섯 곳 방문 후 완주가 표시된다.
4. 여권 진행 중 언어·시간대 변경, 새로고침을 해도 수집 상태가 유지된다.
5. 이미지 실패·저장 실패·새 게임 상태에서도 이동과 복귀가 가능하다.
6. 모바일 세로 화면에서 이동·상세 스크롤·뒤로가기 조작이 충돌하지 않는다.
7. 빌드·타입 검사와 핵심 진행 상태 검증을 수행하고 브라우저 콘솔 오류를 확인한다.
8. 60fps를 목표로 프레임 시간을 측정한다. 측정 기기·브라우저를 명시하며, 에뮬레이션 결과를 실기기 검증으로 표시하지 않는다.

## 9. PRD에서 별도로 결정·보정할 점

**지도 범위:** §4.1의 bbox는 위도 37.535~37.556, 경도 127.045~127.070이다. 같은 문서 §5.3에 적힌 서울숲 좌표의 경도 127.0376은 서쪽 경계 밖이고, 뚝섬한강공원 좌표의 위도 37.5292·경도 127.0715도 밖이다. 문서가 포함하려는 지역과 추출 범위가 일치하지 않는다. 이는 문서 내부 비교 결과다. 실제 지리·마스터 폴리곤은 본 지도 구축 전에 확인해야 한다.

**UI 데모와 Phase 0:** 수작업 샘플 골목으로 도보 UX·화면 전환·수집 재미를 볼 수 있다. PRD Phase 0의 OSM 자동 생성, 실제 도로 위상 보존, 1/3·1/5·1/8 압축 비교, 수작업 보정 공수 산출은 여전히 별도의 검증이다. 이번 데모 완료를 Phase 0 통과로 취급하지 않는다.

**사진·3D:** 현재 제공된 원본이 없다. 사진 준비 상태와 빈 화면은 만들 수 있지만, 실제 공간과 도트 사이 전환의 설득력을 검증하려면 최소 한 장소의 적법하게 확보한 실사 사진이 필요하다. 3D 뷰어의 기술적 구현 가능성과 매장 스캔 콘텐츠 확보 가능성도 별도로 판단한다. glTF 일반 모델의 지원 사실을 Gaussian Splatting 지원 증명으로 사용하지 않는다. [Godot 3D 형식 문서](https://docs.godotengine.org/en/stable/tutorials/assets_pipeline/importing_3d_scenes/available_formats.html)

**국적별 관심도:** 언어 설정과 국적은 서로 다른 정보다. 후속 B2B 리포트는 우선 언어별 관심도로 정의하고, 국적 지표를 사용할 근거는 따로 결정한다. 데모에서 가상의 수치를 실제 사용자 집계처럼 제시하지 않는다.

**데이터 출처:** 실제 OSM 데이터를 도입할 때 귀속 표시와 데이터 배포 조건을 적용해야 한다. PRD의 “앱 내 사용은 문제없음”만으로 모든 사용·배포 방식을 판단하지 않는다. 이번 샘플 맵은 실제 OSM 파생 지도가 아니므로 OSM 기반 재현으로 표시하지 않는다. [OSM 공식 라이선스 안내](https://www.openstreetmap.org/copyright)

## 10. 이번에 선택할 항목

핵심 선택은 1·2·3안 중 어느 경로로 시작할지다. 2안을 고르면 다음을 초기 가정으로 제안한다.

- 브라우저 데모, 모바일 세로 화면 우선.
- 32px 탑다운 도트, 작은 골목, 장소 5곳, 코스 1개.
- 중립적인 지역 산책 콘셉트, EN/JA.
- 가상 장소와 자체 임시 아트. 사진은 준비 상태부터 시작.
- 서버 없이 로컬 저장. 3D는 코어 완성 후 별도 판단.

앵커 고객, POPPLY 제휴, 유료 상품 구조는 이 임시 UI 검증의 선행 조건으로 두지 않는다. 실제 지역 맵·브랜드 자산·상용 파이프라인을 확정하는 단계에서 PRD의 미결정 항목을 해소한다.
