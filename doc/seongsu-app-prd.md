## 1. 개요

### 1.1 배경

성수동은 현재 서울에서 가장 밀도 높은 브랜드 공간 실험장이다. 그러나 방한 외국인 관점에서 성수동은 진입 장벽이 크다.

- 골목 구조가 복잡하고, 랜드마크가 간판 없이 존재하는 경우가 많다
- 대부분의 매장 정보가 한국어 전용이며, 검색은 네이버·인스타그램에 파편화되어 있다
- 팝업스토어의 수명이 2~4주로 짧아 어떤 가이드북도 최신성을 유지하지 못한다

동시에 브랜드 측에는 "외국인에게 우리 공간을 어떻게 알리는가"라는 미해결 과제가 있다. 2026년 7월 Roblox × 무신사 성수 팝업은 "가상 → 오프라인" 방향의 수요를 대형 사례로 증명했다. 본 제품은 그 **역방향(오프라인 → 가상)** 을 노린다.

### 1.2 문제 정의

| 대상 | 문제 |
|---|---|
| 외국인 방문자 | 방한 전에 성수동을 "감각적으로" 파악할 방법이 없다. 지도 앱은 위치는 주지만 분위기·동선·맥락을 주지 못한다 |
| 성수동 브랜드/매장 | 외국인 대상 사전 인지 채널이 없고, 어떤 국적이 무엇에 반응하는지 측정할 수단이 없다 |

### 1.3 제품 한 줄 정의

> 클래식 RPG 감성의 도트 맵으로 성수동을 걸어보고, 명소에서는 실사 사진과 3D로 실제 공간을 확인하며, 방한 전에 나만의 성수 코스를 완성하는 앱.

### 1.4 제품 원칙 (Product Principles)

1. **1:1 스케일 금지.** 골목의 위상(연결 관계)만 보존하고 물리적 거리는 압축한다. 실측 재현은 지루함의 다른 이름이다.
2. **광고는 아이템의 형태로만 존재한다.** 파트너 매장이 배너·팝업으로 노출되는 순간 제품은 실패한다.
3. **디테일 밀도 > 지역 정확도.** 건물 개수보다 지나가는 오토바이 한 대가 더 큰 몰입을 만든다.
4. **도트와 실사는 절대 같은 화면에 섞지 않는다.** 레이어를 전환한다.

## 2. 목표 및 성공 지표

### 2.1 Goals

- G1. 방한 전 외국인이 성수동의 공간 구조와 대표 장소를 30분 내에 파악할 수 있게 한다
- G2. 파트너 브랜드에게 "국적별 관심도"라는 측정 가능한 지표를 제공한다
- G3. 데이터 갱신 비용을 유저 기여로 상쇄해 연간 유지비를 통제한다

### 2.2 Non-Goals (명시적 제외)

- ❌ 정밀 지도 서비스 — 네이버·카카오·구글이 이미 한다
- ❌ 실시간 GPS 위치 기반 플레이 — 방한 전 유저가 사용 불가, 위치기반서비스 신고 의무 발생, 배터리 소모
- ❌ 오픈월드 자유도 — 2인 팀 규모에서 개발 파산
- ❌ 실사 3D 도시 재현 — §5.4 라이선스 제약 참조
- ❌ 예약·결제 기능 (Phase 3 이후 재검토)

### 2.3 성공 지표

| 구분 | 지표 | 초기 목표 |
|---|---|---|
| Engagement | 세션당 평균 체류 시간 | 8분 이상 |
| Engagement | 스탬프 수집 완료율 (코스 1개 기준) | 40% 이상 |
| Retention | D7 재방문율 | 15% 이상 |
| B2B | 파트너 매장 상세 진입률 (노출 대비) | 25% 이상 |
| B2B | 유료 파트너 수 | Phase 2 종료 시 10곳 |
| Data | 유저 기여(가게 존재 확인) 응답 수 | 월 300건 |

## 3. 타깃

### 3.1 최종 사용자 (User)

**Persona A — 방한 예정자 (주 타깃)**
- 20~30대, 일본·대만·동남아·영어권
- 방한 2~8주 전, 인스타에서 성수동을 봤지만 어디가 어딘지 모름
- 니즈: "하루에 뭘 어떤 순서로 볼지" 대략의 그림
- 사용 맥락: 출퇴근 지하철, 자기 전 침대

**Persona B — 방한 중 여행자 (부 타깃)**
- 성수동 현장 또는 숙소에서 다음 행선지 탐색
- 니즈: 혼잡 회피, 근처에 뭐가 더 있는지

### 3.2 유료 고객 (Customer, B2B)

- 성수동 소재 브랜드 플래그십·쇼룸·카페
- 팝업스토어 운영 대행사
- 성동구청 / 서울관광재단 등 공공 (앵커 고객)

**중요:** User와 Customer가 분리된 구조다. 제품 결정 시 항상 "유저 재미가 먼저, 광고 가치는 그 결과"라는 순서를 지킨다.

## 4. 범위 정의

### 4.1 공간 범위 (Spatial Scope)

**⚠️ 최우선 확정 사항.** "성수동"의 경계가 데이터셋마다 다르다 (법정동 성수동1·2가 / 행정동 4개 / 상권 영역 / 실시간 데이터 관측 지점). 하나의 마스터 폴리곤을 먼저 정의하지 않으면 모든 데이터 조인이 어긋난다.

**제안 범위 (MVP):**
- 서쪽: 서울숲 / 뚝섬역
- 동쪽: 성수역
- 남쪽: 뚝섬한강공원 진입로
- 북쪽: 아차산로
- 실측 bbox: `37.535, 127.045 ~ 37.556, 127.070` (약 1.5km × 1.2km)

**게임 내 압축 후 목표 크기:** 도보 종주 3~4분 (실제 1:1은 약 20분 → 1/5 압축)

### 4.2 언어 범위

- MVP: 영어, 일본어
- Phase 2: 중국어 번체, 한국어
- 근거: 성수동 방문 외국인 구성 및 팀 언어 역량

### 4.3 시간 범위

- 3개 시간 슬롯: 아침(09~12) / 오후(12~18) / 밤(18~23)
- 실시간 API 미사용 (§5.2)

### 5.2 D4 (길단위인구) 활용 상세 — 실시간 대체 방식

실시간 API 없이 시간대 연출을 구현한다.

```
NPC 밀도 = 골목별 기준값(D4 분기 데이터)
         × 시간대 계수(아침/오후/밤)
         × 요일 계수(주중/주말)
```

- D4는 상권별·요일별·시간대별·성연령별 길단위인구를 제공하므로, NPC의 **수뿐 아니라 구성(연령·성별)** 까지 차등 가능
- 앱에 정적 테이블로 내장 → 서버 불필요, 오프라인 동작, 장애 없음
- 분기 1회 앱 업데이트 시 갱신

### 5.3 D5 (실시간) 판단 — Phase 3으로 유보

성수동 내 관측 지점 4곳이 이미 존재함을 API 직접 조회로 확인:

| 장소명 | 분류 | 좌표 |
|---|---|---|
| 성수카페거리 | 발달상권 | 37.5430, 127.0566 |
| 뚝섬역 | 인구밀집지역 | 37.5483, 127.0461 |
| 서울숲공원 | 공원 | 37.5430, 127.0376 |
| 뚝섬한강공원 | 공원 | 37.5292, 127.0715 |

**유보 사유:** 지점 단위라 성수동 전체가 사실상 4개 폴리곤. 골목 해상도가 없어 도트 맵의 골목별 연출에 직접 매핑되지 않는다. "지금 성수 붐빔 지수" 같은 단일 위젯으로만 가치가 있으므로 Phase 3에서 재검토.

## 7. 기술 아키텍처

### 7.1 맵 생성 파이프라인

```
Overpass API (성수 bbox)
  ↓ 건물 폴리곤 / 도로 way / POI
GeoJSON
  ↓ 좌표 변환 (WGS84 → EPSG:5179)
그리드 스냅 (타일 4~8m 단위)
  ↓ 룰 기반 타일 배치
TMX (Tiled 포맷) 자동 생성
  ↓ ⚠️ 필수: 아트팀 수작업 보정 (거리 압축 / 디테일 추가)
최종 TMX
  ↓
Godot 4 런타임
```

**핵심 참조:** [Arnis](https://github.com/louis-e/arnis) — OSM + 고도 데이터를 Overpass API로 가져와 룰 기반·결정론적으로 마인크래프트 복셀 월드를 생성하는 Rust 오픈소스(Apache-2.0). AI를 사용하지 않는 순수 룰 기반 변환 구조가 본 파이프라인과 1:1 대응한다. Processing Pipeline 섹션이 설계 참조점.

**자동 생성은 초안이다.** 파이프라인에 수작업 보정 단계가 반드시 포함되어야 하며, 이를 생략하면 "정확하지만 심심한" 맵이 나온다.

### 7.2 기술 스택

| 레이어 | 선택 | 근거 |
|---|---|---|
| 게임 엔진 | **Godot 4** | 2D 도트 + 3D 뷰어 동시 처리, 로열티 없음, 모바일 빌드 용량 작음 |
| 맵 편집 | Tiled (TMX) | 업계 표준, Godot 임포트 애드온 존재 |
| 데이터 전처리 | Python (GeoPandas / Shapely) | 팀 역량 및 GIS 생태계 |
| 3D 명소 | glTF, 포토그래메트리 or Gaussian Splatting | §11 R-04 |
| 보조 (3D 배경 매싱) | OSM2World | 필요 시 |
| 백엔드 | Supabase | 로깅·기여 데이터 수집용 최소 구성 |

### 7.3 데이터 갱신 주기

| 데이터 | 주기 | 방식 |
|---|---|---|
| 맵 지오메트리 | 연 1~2회 | 수동 리마스터 |
| 점포 마스터 (D2/D3) | 분기 | 배치 |
| 길단위인구 테이블 (D4) | 분기 | 앱 업데이트 동봉 |

### 7.4 오프라인 동작

MVP는 **완전 오프라인 동작**을 목표로 한다 (로깅만 온라인). 방한 예정자가 지하철에서 사용하는 시나리오, 그리고 서버 비용 통제를 위해서다.

## 8. 아트 디렉션 규칙

1. **월드는 100% 도트.** 예외 없음.
2. **실사·3D는 전용 프레임 안에서만.** 전환 애니메이션으로 경계를 명시한다.
3. 팔레트: 성수 시그니처인 붉은벽돌 톤을 기조로 한 제한 팔레트(32~48색)
4. 타일 해상도: 16×16 또는 32×32 (착장 스프라이트 제작 단가와 직결 → §13 Q3에서 확정)
5. 아바타 스프라이트: 4방향 × 걷기 3프레임 (8방향은 비용 대비 효과 낮음)

## 9. B2B 상품 구조

| Tier | 제공 | 원가 부담 |
|---|---|---|
| 무료 등재 | 익명 도트 건물로 맵에 존재 | 자동 생성 (원가 0) |
| Tier 1 | 도트 간판 + 실사 카드 + 3개국어 소개 | 사진·카피는 파트너 제공 (계약 조항) |
| Tier 2 | 3D 스캔 내부 투어 | 촬영비 별도 |
| Tier 3 | **국적별 관심도 리포트** | 마진 최대 |

**전략적 요점:** 큐레이션 원가(사진·다국어 카피·촬영 협조)를 **입점 계약서 조항으로 파트너에게 이전**하는 것이 B2B 모델을 택한 핵심 이유다. 계약서 초안에 반드시 반영한다.

**Tier 3이 실질 수익원이다.** 이 앱의 진짜 산출물은 광고 지면이 아니라 "어느 국적 유저가 성수의 어떤 공간에 반응하는가"라는 선호 데이터다.

|---|---|
